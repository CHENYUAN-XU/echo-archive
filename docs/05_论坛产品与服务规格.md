# 论坛产品与服务规格（参照成熟论坛，不复制界面）

## 1. 定位与参照原则

论坛要有“长期使用的真实社区”感，但不照抄贴吧的界面或内容。功能结构参考成熟论坛共同验证过的能力：板块/标签、主题与楼层、个人页、搜索、草稿、通知、举报、权限和运营后台。

NodeBB 的公开文档说明了实时讨论、REST API、插件扩展，以及按版块细分的查看、发帖、回复权限；Discourse 的产品功能覆盖草稿、编辑历史、私信、附件、举报审核队列、置顶和私密空间。这些说明它们不是“锦上添花”，而是社区可持续运行的基础。 [NodeBB 文档](https://docs.nodebb.org/)、[Discourse 功能说明](https://discourse.org/features)

**不将任何外部论坛程序直接嵌入游戏。**游戏任务状态、氛围 UI、AI 角色、单机快照与 Steam 身份都需要深度定制。我们参照它们的模块与治理方法，自建适配游戏的服务。

## 2. 信息架构

```text
首页
├─ 动态流：关注内容、系统通知、订阅板块的新内容
├─ 板块：公告 / 求助 / 地点讨论 / 档案 / 闲聊（具体名称后定）
│  ├─ 标签：地点、现象、状态、难度、时间
│  └─ 主题帖：首楼 + 楼层 + 附件 + 事件状态
├─ 搜索：全文、作者、标签、时间、状态筛选
├─ 收件箱：@提及、回复、关注、私信、系统消息
├─ 用户主页：发帖、回复、收藏、徽章、公开档案
├─ 草稿箱与收藏夹
└─ 管理后台：内容、举报、用户、权限、AI、数据看板
```

游戏任务帖是主题帖的一个**类型**，不是另一套系统：它多出 `caseId`、状态、地点线索与官方更新节点。因此普通社区内容和任务内容共用楼层、搜索、通知和审核。

## 3. 分层功能清单

| 层级 | 首个可上线版本 | 后续增强 | 明确延后 |
| --- | --- | --- | --- |
| 阅读 | 首页、板块、主题、楼层、续读 | 关注流、热度排序、相关帖 | 黑箱推荐算法 |
| 创作 | 发帖、回帖、编辑、删除、草稿 | 引用、投票、附件、协作帖 | 任意 HTML/脚本 |
| 社交 | 资料页、@、收藏、通知 | 关注、私信、徽章、黑名单 | 公开真实身份资料 |
| 发现 | 关键词、标签、作者、时间筛选 | 同义词、纠错、搜索建议 | 未审核内容外部索引 |
| 治理 | 举报、隐藏、禁言、封禁、审计 | 可信等级、申诉、批量审核 | 无审计的删除 |
| 游戏连接 | 任务帖状态、线索同步、离线快照 | 队伍进度、活动 | 玩家帖直接触发关键任务 |
| AI | 受控角色回复、明确标识、日志 | 延迟互动、角色关系网 | 无限自动公开发言 |

## 4. 数据模型

所有记录用 UUID；时间统一 UTC；编辑保留版本和审核痕迹。

```text
boards(id, slug, visibility, posting_policy, sort_policy)
tags(id, slug, label, board_scope)
users(id, steam_id?, name, avatar_key, status, created_at)
profiles(user_id, bio, visible_fields, trust_level)
threads(id, board_id, author_id, title, kind, status, pinned_at, locked_at, last_post_at)
posts(id, thread_id, author_id, parent_post_id?, body_source, body_safe, state, created_at)
post_revisions(id, post_id, editor_id, body_source, reason, created_at)
thread_tags(thread_id, tag_id)
attachments(id, post_id, object_key, mime, bytes, scan_state)
subscriptions(user_id, target_type, target_id, level)
notifications(id, recipient_id, kind, payload, read_at)
reports(id, reporter_id, target_type, target_id, reason, state)
moderation_actions(id, actor_id, target_type, target_id, action, reason, expires_at)
```

任务专用扩展表只保存游戏字段：

```text
case_threads(thread_id, case_id, official_state, reveal_policy)
case_progress(owner_type, owner_id, case_id, state, revision, updated_at)
```

`owner_type` 预留 `player` 与 `party`，单人档升级为队伍进度时无需改数据模型。

## 5. 帖子生命周期与内容安全

```text
草稿 → 提交 → 自动校验 → 已发布
                   ├─ 命中风险 → 待审核 → 发布 / 拒绝
                   └─ 用户举报 → 审核队列 → 隐藏 / 恢复 / 处罚

已发布 → 编辑（保留修订）/ 作者删除（软删除）/ 版主隐藏 / 锁帖 / 归档
```

- 内容使用 Markdown 的**受限子集**。服务端解析、过滤后生成安全展示版本；客户端只渲染安全版本。
- 删除均为软删除；到数据保留期后才由后台作业清理。
- 附件先上传临时区，完成大小、类型、病毒与图片安全检查才给正式地址。
- 置顶、精华、锁帖、官方标识是独立字段，绝不靠标题前缀模拟。

## 6. API 契约和实时机制

```text
POST /v1/auth/steam-ticket        # Steam 票据换取本站会话
GET  /v1/me
GET  /v1/boards
GET  /v1/threads?board=&tag=&cursor=&sort=
POST /v1/threads
GET  /v1/threads/{id}
POST /v1/threads/{id}/posts
PATCH /v1/posts/{id}
POST /v1/reports
GET  /v1/notifications
POST /v1/cases/{id}/sync
WS   /v1/realtime
```

- 请求与响应都有 JSON Schema；API 只增加字段，不偷偷改变旧字段含义。
- 写操作带幂等键，断线重试不会重复发帖或重复结算。
- REST 负责读取和可重试写入；WebSocket 只推送“有更新”。客户端按 `revision` 拉增量，断线后按游标补取，失败再刷新页面。
- 单帖、单用户、单 IP 分别限流；高峰允许降级为轮询。

## 7. 身份、权限与治理

Steam 是首发身份来源：客户端提交短期票据，服务器验票成功后以 SteamID 绑定本站 `User`；绝不相信客户端自称的 SteamID。Steam 官方要求安全服务器验证会话票据，且票据须按会话正确结束。 [Steamworks 身份验证](https://partner.steamgames.com/doc/features/auth?l=english)

权限采用 `actor + action + resource`：

```text
can(user, "thread.reply", thread)
can(moderator, "post.hide", post)
can(ops, "ai.schedule", persona)
```

禁止只在前端隐藏按钮。NodeBB/Flarum 都以按版块或资源粒度的授权来实现社区能力，本项目也由服务器在每一次请求执行同一套判断。 [NodeBB 权限](https://docs.nodebb.org/activitypub/privileges/)、[Flarum 授权](https://docs.flarum.org/extend/authorization/)

初期角色：游客、已验证玩家、受限玩家、版主、内容运营、管理员、官方 AI。角色之外用权限字符串授权，避免新增职位时重写判断。

## 8. AI 账号细则

- 每个 AI 帐号有可见“官方自动化角色”标识、允许板块、预算、冷却时间和紧急停用开关。
- 任务关键结论只能来自官方内容节点，不来自模型自由发挥。
- AI 输入只取过滤后的必要摘要；用户帖中的指令不能改变系统提示、权限或工具调用。
- 输出经历：格式校验 → 安全检查 → 人设检查 → 风险分类 → 自动发布/延迟/人工审核。
- 保存提示词版本、上下文摘要哈希、模型版本、输出、成本和处理结果，支持重放和撤回。
- 首版不用真实模型：先用可配置回复池和定时器，验证社区节奏和审核流程。

## 9. 论坛验收顺序

1. 本地快照能驱动单机游戏，关闭网络不影响完成一件事件。
2. 小型内测：Steam 登录、发帖回帖、通知、举报、人工审核。
3. 压测和安全测试通过，再开 AI 账号。
4. 有备份恢复演练和审核值班规则后，才开放公众注册。
