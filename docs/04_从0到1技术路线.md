# 《留声论坛》从 0 到 1 技术路线（不含剧情）

## 1. 项目边界

这是一个“先单机调查、后可扩展联机 + 在线论坛社区”的混合项目：

- 游戏客户端负责论坛浏览、地图探索、交互、存档和关键 3D 演出。
- 服务端负责账号、真实玩家发帖回帖、AI 账号、审核、活动数据与同步。
- 首发以单人调查体验为准；联机从第一天预留，但不承诺在首发实现。
- 论坛不是菜单贴图，而是可独立运行的线上产品；离线时游戏仍可运行预置内容。
- 本文只规定技术与生产流程。任务、鬼怪、人物、单元剧情都由后续内容管线填充。

## 2. 总体架构

```text
Steam 客户端（Unity 6）
├─ 游戏层：移动 / 探索 / 交互 / 道具 / 存档 / 演出 / 会话抽象
├─ 论坛层：帖子 / 楼层 / 私信 / 通知 / 搜索 / 举报
├─ 内容层：任务包 / 地点包 / 规则包 / 本地预置论坛快照
└─ 网络层：登录、REST 请求、实时消息、断线重连
             │ HTTPS / WebSocket
             ▼
线上服务（Node.js + TypeScript）
├─ API：账号、论坛、任务状态、存档同步
├─ 实时服务：新帖、回复、通知、在线状态
├─ AI 调度：角色人设、上下文、审核、频率控制
├─ 管理后台：审核、封禁、置顶、内容发布、运营日志
└─ 作业服务：AI 延迟回复、通知推送、搜索索引、备份
             │
             ├─ PostgreSQL：账号、论坛、关系、任务状态
             ├─ Redis：会话、限流、队列、实时事件
             ├─ 对象存储：头像、附件、截图
             └─ 监控与备份：日志、错误、数据库备份
```

## 3. 技术选型与原则

### 客户端：Unity 6（推荐）

原因：本项目 UI、数据驱动和网络服务比重很高，同时只需要少量关键 3D 场景；Unity 做论坛 UI、跨平台 Steam 发布、数据与工具链的性价比更稳。关键演出可以使用 HDRP/URP、Timeline、Cinemachine，不需要为了少数 3D 段落让全项目承受 UE5 的制作成本。

若后续明确要“全程高规格 3D 探索”，再将客户端切到 UE5；服务器、数据库和论坛协议仍可保留，避免推倒重来。

### 服务端：Node.js + TypeScript

- HTTP API：Fastify 或 NestJS（二选一，开工时固定）。
- 实时通信：Socket.IO 或原生 WebSocket。
- 数据库：PostgreSQL；ORM 选 Prisma 或 Drizzle。
- 队列/缓存：Redis + BullMQ。
- 部署：Docker Compose 起步，正式环境使用托管 PostgreSQL、Redis 与对象存储。

### 关键原则

- **客户端永远不保存 AI 密钥和管理员权限。**
- **剧情/任务数据与程序逻辑分离。**客户端只读取已发布内容包。
- **论坛线上化与游戏可离线游玩分层。**离线只能浏览预置快照和完成单机任务；联网后再取得社区内容。
- **单人逻辑与联网传输分层。**所有调查行为先写成“命令 → 状态变化 → 事件”；未来联网只替换验证者和同步来源，不改写任务、UI 或地图逻辑。
- **AI 不假装真人。**界面明确为官方 AI 角色/自动化账号，并受到频率、权限与审核控制。
- **所有玩家内容默认需要治理。**从第一天就设计举报、删除、封禁、限流和日志，而不是上线后补。

## 5. 先做什么：垂直切片而非大而全

第一个可玩的目标不是“做完整论坛”，而是完成一条不含正式剧情的闭环：

```text
启动游戏 → 浏览预置帖子 → 接收调查标记 → 进入灰盒地点
→ 找到线索 / 使用一个道具 → 完成事件状态 → 返回论坛
→ 帖子状态、回复、玩家档案和存档一起更新
```

这条闭环必须先使用假文本、假地图、占位音效。它验证产品是否有操作感，以及论坛和探索是否真的互相驱动。

## 6. 分阶段开发流程

| 阶段 | 目标 | 交付物 | 通过标准 |
| --- | --- | --- | --- |
| 0. 预制作 | 锁定范围与技术决策 | 技术路线、风险表、原型目标、代码规范 | 不再同时押注多种引擎 |
| 1. 灰盒闭环 | 跑通一件占位事件 | 可移动地图、交互、论坛状态回写、本地存档 | 新玩家 10 分钟能独立完成闭环 |
| 2. 论坛 MVP | 真实论坛的最小线上能力 | 注册、资料页、发帖回帖、通知、举报、审核后台 | 可控地让小范围玩家同时使用 |
| 3. 内容管线 | 让团队能持续制作事件 | 任务数据格式、编辑工具、校验器、测试场景 | 不改代码可新建一件事件 |
| 4. 联机与 AI | 社区和 AI 稳定接入 | WebSocket、限流、审核队列、AI 调度、成本面板 | 压测与滥用测试达标 |
| 5. 正式制作 | 并行生产地图、UI、音画、事件 | 可发布 Alpha、可回归测试版本 | 每次更新不破坏旧存档 |
| 6. Steam 测试 | 封测与商店准备 | Steam 测试分支、崩溃上报、商店素材、隐私条款 | 封测数据支持上线判断 |
| 7. 发售与运营 | 稳定上线、持续更新 | 发布流程、值班表、备份、补丁与内容发布工具 | 能回滚、有事故响应流程 |

## 7. 客户端模块拆分

### 7.1 游戏基础层（最先落地）

- 输入、镜头、角色移动、碰撞、可交互物。
- 状态机：探索、对话、论坛、背包、演出、暂停。
- 存档：本地多槽位、版本号、迁移机制、损坏备份。
- 设置：分辨率、音量、键位、字幕、辅助功能。

### 7.2 事件运行时

每个事件只允许通过标准接口影响游戏：

```text
事件状态：未发现 → 已追踪 → 调查中 → 已解决 / 已搁置
输入：地点、线索、规则、道具、选择
输出：帖子变化、地图开放、物品变化、演出触发、存档标记
```

不要把事件条件写死在 UI 或地图脚本里；使用 JSON/ScriptableObject 数据定义，必要逻辑放进可复用节点。

### 7.2.1 为联机预留的运行时边界

单机阶段由本地 `CaseSession` 持有状态，但 UI、地图物件和道具不能直接改字段，只能发送命令：

```text
玩家点击交互点 → TryInteract(interactableId)
→ CaseSession.Validate(command) → CaseSession.Apply(command)
→ DomainEvent（线索取得 / 门开启 / 事件完成）
→ UI、存档、音画表现分别订阅事件
```

未来组队时，只把 `CaseSession` 换成“向房主或专用服务器提交命令，再接收权威状态”的实现；同一份任务数据、UI 和演出规则保持不变。状态明确分为：个人状态（笔记、设置）、队伍状态（地点、共享线索、机关）和服务器权威状态（房间、重连、结算）。详见 `06_单机到联机演进设计.md`。

### 7.3 论坛客户端

- 帖子列表、正文、楼层、分页、草稿、引用、搜索、通知。
- 网络状态明确显示：离线快照 / 已同步 / 正在重连。
- 游戏论坛与真实社区视觉一致，但用户内容不能阻塞单机主线。
- 论坛只显示服务器下发的经过净化内容，禁止直接渲染 HTML。

### 7.4 Steam 接入（后期接入，早期预留接口）

- Steam 登录身份票据在服务端验证，不信任客户端自报 SteamID。
- Steam Cloud 同步本地存档（与服务器任务状态区分）。
- 成就、截图、测试分支、崩溃报告。
- 先做可脱离 Steam 的 `IPlatformService` 接口，避免开发期被平台 SDK 卡住。

## 8. 服务端模块与数据模型

### 最小实体

```text
User / Profile / Session
Board / Thread / Post / Draft / Tag
Notification / Report / ModerationAction
CaseDefinition / CaseProgress / PlayerSavePointer
AiPersona / AiJob / AiMessageAudit
Attachment / AuditLog / Ban / RateLimitEvent
```

### 权限

- 游客：浏览公开内容。
- 玩家：发帖、回帖、编辑自己的内容、举报。
- 版主：处理举报、隐藏内容、临时禁言。
- 内容运营：发布官方事件与 AI 行为计划。
- 管理员：账号、权限、数据与紧急开关。

每个接口都需要认证、权限检查、输入校验、审计日志和限流。

### AI 账号的正确接法

1. 先由规则引擎挑选“该不该回复、哪一个角色、回复意图”。
2. 取经过压缩和脱敏的必要上下文，不把整站内容丢给模型。
3. 模型只生成候选文本；服务端进行敏感词、安全、格式与人设校验。
4. 高风险/官方主线回复进入人工审核或延迟发布队列。
5. 记录调用成本、提示词版本、输出、用户举报结果，支持停用和回滚。

没有预算和审核能力时，AI 角色先使用人工编写的回复池 + 规则分支；接口保持一致，后续再替换为模型。

## 9. 内容生产管线

每件事件由一个独立内容包组成，不直接修改程序：

```text
case-id/
├─ case.json            # 状态、条件、奖励、开放地点
├─ forum-seed.json      # 官方帖、预置回复、更新节点
├─ location/            # 场景引用与交互点定义
├─ rules.json           # 规则与验证条件
├─ presentation.json    # 镜头、音频、特效触发点
└─ localization.csv     # 文本本地化键
```

发布前自动做四类检查：字段完整性、状态是否可达、引用资源是否存在、文本/标签是否合规。再用自动化“从头完成事件”的测试档验证不会卡关。

## 10. 测试与质量门槛

- 单元测试：状态机、任务条件、权限、限流、存档迁移。
- 接口测试：注册、登录、发帖、删除、举报、封禁、断线重连。
- 内容测试：每个事件有可重复的通关测试脚本。
- 压力测试：发帖洪峰、WebSocket 连接、AI 队列积压。
- 安全测试：XSS、SQL 注入、越权、刷帖、恶意附件、提示词注入。
- 游戏测试：帧率、崩溃率、存档损坏、Steam 覆盖层、不同分辨率。

每个阶段只能在“可打包、可回归、可恢复存档”后进入下一阶段。

## 11. Steam 上线流程

1. 建立 Steamworks 应用与商店草稿，确定年龄分级、隐私政策、社区规则。
2. 接入 Steam 测试分支，先邀请小范围封测玩家。
3. 加入崩溃上报、服务器监控、数据库每日备份、紧急只读模式。
4. 封测重点看：闭环完成率、卡关点、论坛滥用、AI 成本、服务器峰值与存档问题。
5. 做一次发售演练：新版本发布、数据库迁移、回滚、禁用 AI、关闭发帖、恢复备份。
6. 上线后分开更新：客户端补丁、服务器发布、内容包发布。任何一项都能独立回滚。

## 12. 当前项目的下一步（顺序固定）

1. 新建正式 `client-unity/` 工程，只搭灰盒调查闭环。
2. 将现有 `forum-runtime/` 的接口和数据模型整理为正式 API 契约。
3. 先做本地离线论坛快照 + 存档回写，再接真实账号和在线发帖。
4. 为事件做一个空白内容包和验证器，确保以后“写一集”不等于“改一堆代码”。
5. 完成一条全占位的垂直切片后，才开始确定正式 UI、美术与单元内容。

## 13. 现在不做的事

- 不先制作大量剧情、地图、美术资产或几十个事件。
- 不直接让开放式 AI 自动公开发帖。
- 不在客户端保存数据库密码、模型密钥或管理员令牌。
- 不把联网论坛作为单机主线的唯一前提。
- 不在没有审核、备份、限流前开放给公众注册。
