# 联网技术参考与整合决策

> 研究日期：2026-08-28。本文筛选的是当前有文档、有持续维护、可用于成品的技术；不声称穷尽互联网上每一个产品。每项结论都服务于本项目“先单机、后可选 2–4 人合作、同时有真实论坛”的实际范围。

## 1. 最终建议（一页结论）

```text
首发单人游戏（Unity 6）
├─ C# 领域核心：任务命令、状态机、事件、存档迁移
├─ UI Toolkit：论坛与游戏 UI
├─ Addressables：正式内容包与资源更新
├─ LocalCaseSession：完全离线可玩的调查会话
└─ Steam：启动、身份票据、Cloud、成就、测试分支

线上论坛（自建 Node.js + TypeScript 模块化单体）
├─ PostgreSQL：账号、帖子、关系、审核、任务元数据、全文搜索
├─ Redis：会话、限流、短缓存、可靠后台作业
├─ WebSocket：通知与新楼层提示；REST 负责读写
├─ S3 兼容对象存储：头像/附件，异步扫描后公开
└─ 管理后台：审核、封禁、AI 发布计划、审计、紧急开关

未来组队（现在只做接口和样机）
└─ 优先验证 Unity Netcode for GameObjects；若需要完整会话/匹配/权威游戏服务，评估 Nakama
```

不建议现在引入：微服务集群、Kafka、持续开放世界、开放式 AI 自动发帖、专用游戏服务器群、外部论坛程序的深度改造。它们会让“先做出一条好玩的单机调查闭环”变成无期限的平台工程。

## 2. 已调研的成熟技术与取舍

| 能力 | 成熟技术/参考 | 采用决定 | 原因与边界 |
| --- | --- | --- |
| 游戏引擎 | Unity 6、UE5 | **Unity 6** | 本项目 UI、数据、论坛、偶发 3D 演出比重高；若后来改成全程高规格 3D 才重评 UE5。服务端契约与内容格式不绑定引擎。 |
| 论坛产品 | NodeBB、Discourse、Flarum | **参考，不嵌入** | 它们验证了板块、权限、实时讨论、插件、草稿、编辑历史、审核等能力；游戏需要离线快照和任务联动，直接二次开发成本更高。 |
| UI | Unity UI Toolkit | **采用** | 支持运行时 UI 数据绑定，适合复杂、可滚动、状态频繁变化的论坛界面；视觉仍完全自定义。 |
| 内容资源 | Unity Addressables | **采用** | 内容包、场景、音画资源按组加载；用于正式补丁/内容更新时必须保存每个发布版本的 content state。 |
| 游戏领域逻辑 | 自建纯 C# Core | **采用** | 任务、交互、道具、状态机不能继承网络或 UI 类，否则联机化必然推翻。 |
| 论坛 API | Node.js + TypeScript + Fastify | **采用** | 初期一套语言、强类型契约、开发速度快；保持模块化单体而非过早微服务。Fastify/NestJS 开工时二选一，不能混用。 |
| 核心数据库 | PostgreSQL | **采用** | 论坛关系、事务、审核与修订历史需要强一致关系数据；先用内置全文搜索。中文分词与排序以真实帖子语料压测后决定是否加独立搜索。 |
| 缓存/作业 | Redis | **采用** | 限流、会话、短缓存；可靠的 AI/通知/扫描作业使用 Streams 或队列，不把 Pub/Sub 当可靠任务队列。 |
| 实时通知 | WebSocket + Redis 扇出 | **采用** | “有新回复/通知”的提醒适合推送；最终数据仍从 API 按 revision 拉取，断线不丢状态。 |
| 附件 | S3 兼容对象存储 | **采用** | 文件不进入数据库，也不从 Web 根目录直接执行或暴露；先扫描再发布。 |
| 身份 | Steam 票据 + 本站会话 | **采用** | 首发无需额外密码体系；服务器验票后才创建/绑定本站用户。 |
| Steam 云存档 | Steam Cloud API/Auto-Cloud | **采用，后接** | 单人档可跨设备；Steam Cloud 与服务器上的论坛/队伍状态不是同一个东西。 |
| 2–4 人联机 | Unity NGO | **首选技术样机** | Unity 官方将 NGO 定位于已有 GameObject 单机项目和较小规模、较低复杂度多人；符合“将来可组队调查”。 |
| 权威会话/匹配 | Nakama | **备选，样机后决策** | 提供认证、聊天、通知、匹配和权威/中继会话，但引入第二套服务运行时；只在 NGO 样机确实不足或需要长期运营组队时引入。 |
| 可观测性 | OpenTelemetry | **采用** | 从 API、后台作业和未来游戏会话统一采集 traces、metrics、logs；比将来换监控厂商更稳。 |
| 部署 | Docker Compose（开发/预发） | **采用** | API、worker、PostgreSQL、Redis、本地对象存储的可重复环境；正式环境再替换托管服务。 |
| AI 账号 | Provider Adapter + 规则/审核流水线 | **采用，后开模型** | 先用人工回复池验证体验；模型供应商、模型名和密钥不进入客户端。 |

## 3. 现成论坛能教给我们的，不是“做一张贴吧皮肤”

NodeBB 将实时讨论、REST API、插件框架和细粒度权限作为核心能力；其权限可按分类限制查看、发主题、回复和投票。Discourse 将草稿、编辑历史、私信、附件、举报队列、置顶和私密空间列为默认社区能力；Flarum 把授权表达为“用户是否能对具体资源做某动作”。 [NodeBB](https://docs.nodebb.org/)、[NodeBB 权限](https://docs.nodebb.org/activitypub/privileges/)、[Discourse](https://discourse.org/features)、[Flarum 授权](https://docs.flarum.org/extend/authorization/)

因此本项目的论坛内核必须具备以下独立模块：

```text
Identity        账户、会话、资料、Steam 绑定
Forum           板块、标签、主题、楼层、修订、草稿、收藏
Discovery       排序、游标分页、全文搜索、筛选、续读
Social          订阅、@、通知、私信（后期）
Moderation      举报、队列、隐藏、禁言、封禁、审计、申诉（后期）
GameLink        任务帖、官方状态、离线快照、进度投影
Automation      AI 人设、延迟作业、审批、成本、停用开关
```

这些模块共同使用一套用户、权限、内容状态和审计记录；任务帖不是一套旁路论坛。论坛 UI 只是 `Forum API` 的客户端之一，未来若做游戏官网或运营后台也可以复用接口。

## 4. 目标系统的模块化结构

```text
client-unity/
├─ Domain                 # 纯 C#：Command、Event、CaseSession、存档格式
├─ Application            # 用例：调查、发帖、读取快照、同步、结算
├─ Presentation           # UI Toolkit、场景、镜头、音画；订阅事件
└─ Infrastructure         # LocalSave、HTTP、WebSocket、Steam、未来 NGO/Nakama

server/
├─ api                    # HTTP、鉴权、输入验证、WebSocket 接入
├─ forum                  # 帖子/回复/搜索/通知
├─ moderation             # 举报、策略、审核动作、审计
├─ game-link              # 进度命令、官方任务投影、内容发布
├─ automation             # AI 作业、附件扫描、通知扇出
├─ worker                 # 可靠异步消费者
└─ shared-contracts       # JSON Schema、错误码、事件名、版本
```

依赖只准向内：`Presentation → Application → Domain`；`Infrastructure` 通过接口被 Application 使用。服务端同样禁止 Forum 直接知道 Unity 场景细节，禁止游戏内容包直接调用数据库。

## 5. 三条数据流

### 5.1 单机调查流（必须永远可离线）

```text
输入 → Command → LocalCaseSession 验证/应用 → DomainEvent
     → UI/场景表现
     → 版本化本地存档
     → 更新内置论坛快照的显示状态
```

### 5.2 联网论坛流（社区服务）

```text
Steam 票据 → 服务器验票 → 本站短期会话
→ HTTP 写入（含幂等键）→ PostgreSQL 事务
→ Outbox 事件 → Redis Stream
→ Worker：通知 / 搜索索引 / AI 调度
→ WebSocket 提醒客户端拉取 revision 增量
```

不要让 WebSocket 消息成为帖子真相，也不要让请求成功后再“尽力而为”地发后台任务。使用事务 Outbox：帖子写入和“待发通知事件”在同一个数据库事务提交；worker 之后可重试地处理。

### 5.3 将来队伍调查流

```text
客户端 Command（序号 + 幂等 ID）
→ Host/Authority 验证距离、物品、事件阶段、权限
→ 权威端 Apply → revision 增加 → Event/状态差量广播
→ 客户端表现；缺 revision 时请求快照
```

这里的 `Command/Event` 与单机使用同一套类型。差别只在于单机 `LocalCaseSession` 本地 Apply，联机 `NetworkCaseSession` 等待权威端结果。

## 6. 论坛数据库与检索设计

### 必备表与索引

- `threads(board_id, last_post_at DESC, id)`：板块按活跃排序。
- `posts(thread_id, created_at, id)`：稳定楼层与游标分页。
- `notifications(recipient_id, read_at, created_at DESC)`：未读计数和收件箱。
- `reports(state, created_at)`：审核队列。
- `audit_logs(target_type, target_id, created_at)`：追溯与申诉。
- 帖子标题/正文生成检索向量；标题权重高于正文。

PostgreSQL 自带 `tsvector/tsquery`、排名、词典和索引类型，足以作为首版全站检索的基础。中文帖子必须用真实语料做分词、召回和排序验收；如果不够好，再以独立搜索引擎作为 `SearchProvider` 替换，不改变 Forum API。 [PostgreSQL 全文检索](https://www.postgresql.org/docs/17/textsearch.html)、[检索控制](https://www.postgresql.org/docs/17/textsearch-controls.html)

### 一致性原则

- 发帖、回帖、锁帖、处罚都由 PostgreSQL 事务写入。
- `revision` 单调增加，客户端据此判断是否需要刷新。
- 点赞/阅读数等弱一致数据可异步聚合；帖子正文和审核状态不能。
- 绝不以客户端时间决定帖子顺序、惩罚时效或任务结算。

## 7. Redis、任务队列与实时的正确边界

Redis Pub/Sub 是“连着才收到”的 at-most-once 传输；断线消息不保留。因此只用于在线连接间的低价值提醒。Redis Streams 有持久记录、消费者组、确认和接管未处理消息的能力，适合通知、附件扫描、AI 延迟回复、搜索索引等可重试工作。 [Redis Pub/Sub 语义](https://redis.io/docs/latest/develop/pubsub/)、[Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)

初始作业清单：

```text
post.published       → 生成通知、更新搜索、检查 AI 触发条件
attachment.uploaded  → 类型验证、扫描、缩略图、发布/拒绝
report.created       → 风险分级、审核队列提醒
ai.reply.requested   → 预算检查、生成、审核、定时发布
case.content.release → 校验内容包、生成离线快照、灰度发布
```

每项作业有唯一 `jobId`、重试次数、死信状态和告警；重复消费必须幂等。

## 8. Steam 与存档

Steam 会话票据可以用于客户端到安全后端的身份验证，安全后端验证后才获得 SteamID；票据和 Web API 密钥不能放进客户端。 [Steamworks 身份与所有权](https://partner.steamgames.com/doc/features/auth?l=english)

Steam Cloud 可自动或通过 API 同步游戏文件到玩家的 Steam 账户。它用于单人存档跨设备，而非取代服务器数据库；游戏进度与论坛账户数据分开保存。 [Steam Cloud](https://partner.steamgames.com/doc/features/cloud?l=english)

```text
Local save：个人单机进度、设置、离线快照游标
Steam Cloud：Local save 的加密/压缩副本和冲突元数据
Game backend：论坛身份、玩家公开资料、在线内容、未来队伍状态
```

存档包含 `saveVersion`、`contentVersion`、`caseRevision`、校验和与迁移链。升级时复制旧档 → 迁移 → 校验 → 写新档；任何失败都保留可恢复副本。

## 9. 联机技术的真正选择条件

### 9.1 Unity Netcode for GameObjects（先做样机）

Unity 将 NGO 定位为基于 GameObject/MonoBehaviour 的高层网络 SDK，适合为既有单人 GameObject 项目加入较小规模、较低复杂度的多人能力。它很适合验证 2–4 人共查的同步、房间、RPC、断线与重连体验。 [Unity Netcode 概览](https://docs.unity.com/multiplayer/netcode/netcode)、[NGO 包文档](https://docs.unity3d.com/ja/current/Manual/com.unity.netcode.gameobjects.html)

但不要把任务规则写进 `NetworkBehaviour` 或 RPC 函数；NGO 只能成为 `NetworkCaseSession` 的传输实现。这样即使换服务，也不动领域层。

### 9.2 Nakama（有条件的后续选择）

Nakama 是可自托管的实时游戏后端，提供认证、社交、聊天、通知、匹配和两种多人模型：客户端中继以及服务器权威。权威模式能让服务器验证消息、维护状态和广播结果；但需要编写并运营服务端匹配逻辑。 [Nakama 概览](https://heroiclabs.com/docs/nakama/)、[权威多人](https://heroiclabs.com/docs/nakama/concepts/multiplayer/authoritative/)

只有满足任一条件才立项 Nakama 样机：

- 组队发布已确认，而不只是“留余地”；
- 需要长期房间、匹配、好友/队伍、跨区域会话或服务端反作弊；
- Node 论坛服务不适合承担高频游戏会话。

否则继续用自建论坛后端 + Unity 单机核心，避免账户、通知、群组在两套平台中重复维护。

## 10. AI 角色是运营系统，不是一个聊天框

AI 账号完整流水线：

```text
触发规则 → 选择角色/意图 → 最小必要上下文摘要
→ 输入安全过滤 → Provider Adapter → 结构化候选输出
→ 输出过滤/人设校验/风险分级 → 自动发布或人工审批
→ 记录成本、版本、反馈、撤回能力
```

所有玩家帖子都是不可信数据。OWASP 将提示词注入定义为 LLM 应用的重要风险，推荐输入/输出过滤、结构化分隔、最小权限和高风险人工审批。AI 没有数据库写入、封禁、改任务、读取私信等权限；这些动作必须由普通服务端代码再做权限检查。 [OWASP LLM 提示词注入防护](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

首版顺序：人工编写回复池 → 规则选择和延迟发布 → 审核后台 → 小流量模型试验 → 成本/滥用达标后扩大。绝不先开放“AI 自动像真人一样和所有人聊天”。

## 11. 安全、审核与隐私底线

| 风险 | 必须的工程措施 |
| --- | --- |
| XSS/富文本攻击 | 受限 Markdown，服务端净化，客户端不注入原始 HTML，CSP。 |
| 刷帖/骚扰 | 账号、IP、板块、主题四级限流；新号冷却；举报、隐藏、禁言、封禁、审计。 |
| 恶意附件 | 白名单扩展与实际类型检查、大小限制、应用生成文件名、临时区、扫描、对象存储隔离。 |
| 越权 | 每个写接口执行 `actor + action + resource` 授权；前端隐藏不算权限。 |
| 存档篡改 | 单人本地档允许但不影响线上奖励；未来队伍结算服务端验证。 |
| 密钥泄漏 | 只存部署环境的 Secret Manager；客户端、日志、仓库和内容包不得保存。 |
| AI 注入 | 不信任用户帖、结构化上下文、输出校验、最小权限、审批与停用开关。 |

OWASP 对上传的建议包括服务端验证实际文件类型、应用生成文件名、大小限制、异机/对象存储隔离与扫描；这些要从附件功能第一天做，不是以后“补安全”。 [OWASP 文件上传防护](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 12. 部署、监控与恢复

### 环境

```text
local      Docker Compose：API / worker / Postgres / Redis / MinIO
staging    独立数据库和对象存储；自动部署；不接生产 AI 密钥
production 托管 Postgres + Redis + 对象存储；API/worker 横向扩展
```

Compose 支持依赖健康检查，适合开发和预发可重复启动；生产环境以相同镜像和显式配置发布，但数据库不与 API 容器共生。 [Docker Compose 健康检查](https://docs.docker.com/compose/how-tos/startup-order/)

监控从第一版服务端开始收集：请求 trace、错误率、P95 延迟、WebSocket 在线数、队列积压、数据库连接、附件扫描失败、AI 成本与审核积压。OpenTelemetry 是供应商中立的 traces、metrics、logs 标准，可避免监控实现绑定某一家服务。 [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/)

### 必须演练的恢复场景

1. API 重启：论坛读取可用，WebSocket 自动重连。
2. worker 挂掉：Streams/队列恢复未完成作业，帖子不会消失。
3. 数据库误迁移：从可验证备份恢复到新环境，再切流量。
4. AI 异常：关闭 AI 发布开关，论坛本身保持工作。
5. 内容包错误：停止分发并回退 manifest，旧单机存档仍可打开。

## 13. 从现在开始的实际实施顺序

| 迭代 | 做什么 | 不做什么 | 验收 |
| --- | --- | --- | --- |
| P0 | 建正式仓库、契约、纯 C# Domain、空内容包 Schema | 不接网络、不写正式剧情 | 命令驱动的占位事件可保存/加载 |
| P1 | Unity 灰盒：移动、交互、背包、论坛快照 UI、状态回写 | 不接账号、AI、多人 | 10 分钟完成“论坛→地点→回帖”占位闭环 |
| P2 | 服务器模块化单体：Postgres、论坛 API、审核最小集、管理后台雏形 | 不开放公众注册、无附件 | 内测账号能稳定发帖、回复、举报 |
| P3 | Steam 验票、通知、搜索、对象存储、任务内容发布管线 | 不做无限 AI | 断线重试不重复写入；备份恢复通过 |
| P4 | AI 回复池/审核队列、封闭社区压测 | 不允许模型自由调用工具 | 滥用、成本和故障可控 |
| P5 | 2 人 NGO 灰盒样机 | 不让正式内容依赖联机 | 重连、机关、结算不分歧 |
