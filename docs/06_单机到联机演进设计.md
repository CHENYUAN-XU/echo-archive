# 单机到联机演进设计（避免重写底层）

## 1. 联机目标先分级

“能联机”有三种完全不同的成本，不能混在一起开发：

| 等级 | 玩家体验 | 首发是否实现 | 技术要求 |
| --- | --- | --- | --- |
| A. 异步社区 | 玩家各自调查，在同一论坛交流 | 是 | 账号、论坛服务、进度隔离 |
| B. 组队共查 | 2–4 人进入同一地点，共享线索与机关 | 预留 | 房间、权威状态、同步、重连 |
| C. 持续世界 | 大量玩家同时影响同一世界 | 不做 | 分区、持久世界、反作弊、运营团队 |

项目现在做 A，架构预留 B，明确不为 C 付出成本。这样有真实社区，也不把单人核心体验赌在服务器上。

## 2. 不可变的领域规则

核心逻辑不能依赖 Unity 场景对象或网络组件，按四层隔离：

```text
表现层      Unity UI、动画、场景物件、声音
应用层      UseCase：交互、使用道具、提交调查、结算
领域层      CaseSession、规则、状态机、命令、领域事件
基础设施层  本地存档、HTTP、WebSocket、Steam、未来联机传输
```

领域层的输入输出是普通数据：

```text
Command { type, actorId, targetId, payload, clientSequence }
Result  { accepted, reason?, newRevision, events[] }
Event   { type, entityId, payload, revision }
```

单机时 `actorId` 是本地玩家，`CaseSession` 直接运行；组队时命令送往房主/专用服务器，只有权威端调用 `Apply`。表现层只订阅 Event，不关心状态来自本地或远端。

## 3. 状态所有权

| 数据 | 单机阶段来源 | 组队阶段权威者 | 同步方式 |
| --- | --- | --- | --- |
| 设置、键位、已读 | 本地 | 玩家本地 | 不同步或 Steam Cloud |
| 个人档案、论坛发言 | 服务端 | 服务端 | API + 通知 |
| 单人事件进度 | 本地存档 | 玩家个人档案/服务端备份 | 版本化快照 |
| 队伍地点、机关、共享线索 | 占位接口 | 房主或专用服务器 | 命令 + 状态快照 |
| 随机数与判定 | 本地可复现种子 | 权威端 | 同步种子/结果 |
| 奖励与成就 | 本地暂存 | 服务端验证后确认 | 事务 + 幂等键 |

不能同步的：整个 Unity GameObject、帧间动画状态、玩家自由文本 HTML、客户端声明的奖励。这些都是后期重构和作弊的来源。

## 4. 联机抽象接口

客户端从第一天依赖接口而非某个网络 SDK：

```text
ICaseSession       Start / Dispatch / GetSnapshot / Subscribe
ILocalSaveStore    Load / Save / Migrate
IRemoteProgress    Pull / PushCommands / ResolveConflict
IMatchService      CreateParty / Join / Leave / Reconnect
IRealtimeFeed      Subscribe / Unsubscribe / Resume
IIdentityService   SignIn / SignOut / GetAccessToken
IPlatformService   SteamOverlay / Cloud / Achievements
```

单机提供 `LocalCaseSession`、`JsonSaveStore`、`NullMatchService`。联机新增 `NetworkCaseSession` 和 `Steam/ServerMatchService`，不改调查、UI 或事件包的调用方。

## 5. 存档与版本迁移

每份存档必须包含：`saveVersion`、`contentVersion`、`caseRevision`、`createdAt`、`updatedAt`、状态快照、命令日志摘要和校验和。

升级时：读取旧版本 → 顺序执行迁移器 → 校验任务状态 → 写入新副本 → 保留上一个可恢复副本。未知内容包或字段必须给出恢复提示，不能直接清空进度。

单人档冲突以本地最近完成的有效命令链为准；未来队伍档只接受权威端版本。绝不“合并两个玩家 JSON 存档”。

## 6. 未来组队的网络模型

推荐 2–4 人合作，正式版优先专用服务器权威；封测可用房主权威降低成本，但接口保持一致。

```text
客户端预测（仅移动表现）
→ 发送带序号命令
→ 权威端验证距离、物品、事件阶段和权限
→ revision 递增并广播事件/状态差量
→ 客户端按 revision 应用；缺包则请求快照
```

- 机关、拾取、结算、奖励由权威端判定。
- 移动可预测与插值；调查结果不可预测。
- 命令均有 `partyId`、`actorId`、`commandId`、版本号；重发无副作用。
- 断线保存最近快照和未确认命令；重连由权威端决定重放或丢弃。

Unity 6 目前提供 Lobby、Relay、Matchmaker、Multiplay Hosting 等多人能力，但是否采用其托管服务必须在联机样机中测试成本、地区延迟和并发后决定；它们不能进入领域层。 [Unity 6 文档](https://docs.unity3d.com/Manual/WhatsNewUnity6.html)

## 7. 开发阶段与禁止跨线

### S1：纯单机灰盒

- 不接匹配、不接同步。
- 所有调查交互必须经过 Command/Session 接口。
- 本地存档和离线论坛快照先跑通。

### S2：异步线上社区

- 账号、论坛和个人进度备份上线。
- 游戏仍可完全离线；网络失败只影响社区新内容，不影响单机完成。

### S3：组队技术样机

- 用一张灰盒地图、一件假事件、2 人连接验证同步、掉线重连和结算。
- 样机未通过前，正式地图或内容不能依赖联机机制。

### S4：是否正式做组队

评估成本、稳定性、玩家需求和维护能力。通过则制作 B 级联机；否则保留异步论坛为正式功能，不会形成烂尾式“半联机”。

## 8. 防止牵一发动全身的工程制度

- 模块只能向内依赖：UI 不能访问数据库；任务包不能调用 HTTP；领域层不引用 Unity/Steam SDK。
- 跨模块只通信版本化接口和事件，禁止跨文件直接改状态。
- 每个模块建立契约测试；服务器升级 API 时先保持旧版本兼容。
- 内容包有 Schema 与版本；存档有迁移器；数据库有迁移脚本；发布有回滚。
- 新功能开工前必须写清：改变哪些状态、谁是权威、离线时如何表现、失败如何恢复。
- 每次扩展只选一个入口：新增命令、事件、内容字段或适配器，不能把逻辑散落到地图/UI。

## 9. 联机上线硬门槛

- 断线、重连、房主退出、服务器重启都不会复制奖励或破坏任务。
- 同一命令重发 10 次，状态只变化一次。
- 恶意客户端不能通过修改内存或请求直接获得线索、结算或奖励。
- 4 人连续游玩 60 分钟，没有不可恢复的状态分歧。
- 有服务器监控、限流、封禁和事故回滚方案。
